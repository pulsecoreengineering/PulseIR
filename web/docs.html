PulseIR Schema Reference

PulseIR is a YAML-to-firmware compiler. You describe your hardware, logic, and behaviour in one YAML file or a directory of files linked by imports:; the toolchain generates complete, buildable firmware for Arduino, ESP-IDF, MicroPython, or Zephyr RTOS. The schema supports GPIO, I2C/SPI sensors, LCD and OLED displays, state machines, MQTT, telemetry, safety rules, and more — all without writing C by hand for the common cases.

Quick Start

The smallest useful model: one LED, one task, no state machine. Save this as blink.yaml:

pulseir: "1"

project:
  name: blink

target: esp32

hardware:
  devices:
    led: { type: digital_output, pin: GPIO2 }

parameters:
  blink_ms: { type: int, default: 500, range: [50, 10000], unit: ms }

actions:
  toggle_led: { driver: gpio_control, params: { device: led, value: toggle } }

tasks:
  blink:
    every: blink_ms     # reads the parameter every tick — change at runtime
    do: toggle_led

Generate the Arduino sketch:

node dist/src/cli.js blink.yaml --target arduino
✓ Output: blink/blink.ino + blink/blink_types.h — open in the Arduino IDE and upload.

A state machine is completely optional. If your project only needs periodic tasks and/or serial commands, omit machine: entirely — the generated sketch will be plain Arduino with no HSM overhead.

ℹ Key shape rules: actions:, parameters:, events:, tasks:, and machine.states: are all mappings keyed by name (not lists). machine.transitions: is the one true list. The parser reports a clear error if you use the wrong shape.

Targets & Backends

PulseIR generates complete, buildable firmware for four targets. Pass --target <name> on the CLI to choose one; the default is arduino.

FlagEntry pointOutputStatus
--target arduino (default) setup() + loop() .ino + _generated.h ✅ Production-ready
--target espidf app_main() (FreeRTOS) .cpp + CMakeLists.txt ✅ Production-ready
--target micropython main() (asyncio) main.py ✅ Production-ready
--target zephyr int main() (Zephyr kernel) .cpp + CMakeLists.txt + prj.conf 🔄 In progress — skeleton only
⚠ Zephyr support is in active development. The skeleton compiles for native_sim but GPIO, UART, I2C, networking, and tasks are not yet wired to real Zephyr APIs. See the Zephyr section for the full status and roadmap.

Arduino

Status: fully supported. The default backend — tested against the Arduino IDE, PlatformIO, and the arduino-cli. Models with a machine: block get PulseHSM vendored alongside the sketch; models without it get plain Arduino with no extra include.

Generated files (--outdir)

build/
├── project_name.ino          ← regenerated every run — do not edit
├── project_name_generated.h  ← regenerated every run — do not edit
├── PulseHSM_config.h         ← runtime table sizes, from the model
├── PulseHSM.h / .cpp         ← runtime, vendored
└── src/
    ├── actions.cpp            ← YOURS — written once, never overwritten
    └── guards.cpp             ← YOURS — written once, never overwritten

Build

# Generate
node dist/src/cli.js model.yaml --target arduino --outdir build/

# Or quick single-file output
node dist/src/cli.js model.yaml --target arduino --output sketch.ino

# PlatformIO
pio run -e uno

Notes

  • The task scheduler uses millis() with deadline-advance (not restart) — the average rate is exact even if one loop pass runs long.
  • PulseHSM_config.h is generated from the model's state/event counts. Keep it beside PulseHSM.h or a separate compilation of PulseHSM.cpp will use wrong table sizes silently.
  • ESP32/ESP8266 Arduino core is treated as Arduino — use --target arduino, not espidf. The ESP-IDF target generates native FreeRTOS code without the Arduino layer.

ESP-IDF

Status: fully supported. Targets the native ESP-IDF / FreeRTOS API — no Arduino layer. Use this for production ESP32 firmware where you need FreeRTOS queues, tasks, low-level peripheral control, or memory guarantees that the Arduino core abstracts away.

Generated files (--outdir)

build/
├── main/
│   ├── project_name.cpp      ← regenerated — app_main() + _setup() + while(1)
│   ├── project_name.h        ← regenerated types header
│   ├── PulseHSM.h / .cpp     ← runtime, vendored
│   └── PulseHSM_config.h     ← runtime table sizes
└── CMakeLists.txt            ← ESP-IDF project file

Build

# Generate
node dist/src/cli.js model.yaml --target espidf --outdir build/

# Build and flash (ESP-IDF toolchain required)
idf.py build
idf.py -p /dev/ttyUSB0 flash monitor

Notes

  • Tasks map to esp_timer one-shot callbacks rescheduled on expiry — not FreeRTOS tasks. This preserves the same semantics as the Arduino backend.
  • GPIO uses gpio_set_level() / gpio_get_level(); I2C uses i2c_master_*; ADC uses adc1_get_raw() (ADC2 is reserved when Wi-Fi is active — see HAL checks).
  • PWM uses the LEDC peripheral. The generated code handles the ESP-IDF core 2.x vs 3.x API split automatically.
  • HTTP client uses esp_http_client; MQTT uses PubSubClient (stub — full native MQTT is planned).
  • Also emits a CMakeLists.txt with cmake_minimum_required(VERSION 3.16) and the correct idf_component_register() call.

MicroPython

Status: fully supported. Generates a single main.py that runs on any MicroPython-compatible board (RP2040, ESP32, STM32, and others). The scheduler uses asyncio cooperative multitasking — no RTOS needed.

Generated file

main.py   ← single self-contained file; copy to the board's filesystem

Build

# Generate
node dist/src/cli.js model.yaml --target micropython --output main.py

# Deploy (mpremote or rshell)
mpremote cp main.py :main.py
mpremote reset

Notes

  • Tasks become asyncio.create_task() coroutines with asyncio.sleep_ms(N) loops.
  • GPIO uses machine.Pin; PWM uses machine.PWM; ADC uses machine.ADC; I2C uses machine.I2C; SPI uses machine.SPI; UART uses machine.UART.
  • The state machine is implemented as a pure-Python HSM with the same semantics as PulseHSM — no C extension required.
  • A model with no machine: block generates a plain asyncio loop with no HSM class in it at all.
  • Libraries that are platform-specific (ArduinoOTA, HTTPClient) are replaced with MicroPython equivalents or TODO stubs. Declare third-party libraries in libraries: as normal — the generated file includes a comment listing what to install with mip.

Zephyr RTOS

⚠ Zephyr support is in active development. The backend exists and generates compilable output for native_sim, but most hardware interfaces are not yet wired to real Zephyr APIs. Do not use this target for production firmware yet. The roadmap below shows what is planned and when.

What works today (Phase 1 — skeleton)

  • Generates main.cpp, CMakeLists.txt, and prj.conf
  • Compiles and links for native_sim (no hardware needed)
  • State machine skeleton (PulseHSM vendored alongside)
  • Basic task loop using k_uptime_get()

What does not work yet

  • GPIO — gpio_dt_spec / gpio_pin_set_dt() stubs exist but devicetree is not generated (Phase 2)
  • UART, I2C, SPI — stubs only, no working init (Phase 2–3)
  • PWM, ADC — not yet started (Phase 3)
  • Wi-Fi, MQTT, HTTP, BLE, OTA — not started (Phase 4)
  • app.overlay (devicetree aliases) — not generated (Phase 2)

Planned roadmap

PhaseGoalInterfaces
Phase 1 (current)Skeleton compiles for native_sim—
Phase 2Real GPIO, UART, I2C on ESP32 / nRF52840 / STM32gpio, uart, i2c
Phase 3Tasks → k_timer + system workqueue; PWM, SPI, ADCpwm, spi, adc
Phase 4Networking, MQTT, HTTP, OTA scaffoldswifi, mqtt, ble, ota

Build (skeleton)

# Generate
node dist/src/cli.js model.yaml --target zephyr --outdir build/

# Compile (Zephyr SDK + west required)
west build -b native_sim        # simulation — no hardware needed
west build -b esp32_devkitc_wroom  # real board (Phase 2+)
./build/zephyr/zephyr.exe       # run the native_sim binary

Top-level structure

A PulseIR model is a YAML document with the following top-level keys. All keys except project and target are optional.

pulseir: "1"               # schema version declaration

project:
  name: my_system
  version: "1.0.0"
  description: What this does

target: esp32              # board identifier

hardware:              # buses + devices
  buses: []
  devices: []

events: []             # named events for the state machine
parameters: {}         # runtime-tuneable values
actions: {}            # named driver invocations
tasks: []              # periodic background work
commands:              # line-oriented serial dispatch
  commands: []
machine:               # hierarchical state machine
  states: []
  transitions: []
communication: {}      # selective MQTT publish/subscribe
telemetry: {}          # per-channel sensor publish intervals
safety:                # pre-dispatch safety checks
  rules: {}
diagnostics: {}        # watchdog, heartbeat, log level
libraries: []          # third-party library declarations
imports: []            # include other YAML files

Schema versioning

Declare the schema version at the top of every model file. The current schema version is 1.

pulseir: "1"
  • A model declaring a higher version than the toolchain understands causes a warning (not an error).
  • A model declaring a lower version causes a migration note warning.
  • Omitting pulseir: is silently accepted for backward compatibility.
ℹ The version string is always quoted in YAML ("1", not 1) to avoid integer coercion across schema generations.

hardware:

Declares the physical hardware attached to the board: communication buses and named device components.

hardware:
  buses:
    i2c_bus:             # key = bus name
      interface: i2c
      sda: GPIO21
      scl: GPIO22
      frequency: 400000
  devices:
    led:                 # key = device name
      type: digital_output
      pin: GPIO13

Bus types

hardware.buses is a mapping keyed by bus name. Each entry sets interface: and interface-specific pin/parameter fields directly — there is no binding: wrapper.

ℹ Implicit vs. explicit buses: Simple pin-based devices (digital_input, digital_output, pwm_output, analog_input, dht22/11) do not need a bus entry — the codegen infers the GPIO/PWM/ADC interface from the device type and its pin:. Only shared bus protocols (I2C, SPI, OneWire, UART) and network interfaces (WiFi, MQTT, BLE) need an explicit buses: entry.
InterfaceDirect fieldsDescription
i2c sda, scl, frequency I2C / TWI bus. Multiple devices share one bus entry.
spi mosi, miso, sck, cs, frequency SPI bus. Each device may have its own CS pin in its config.
uart port, baud, tx, rx UART serial port. Used for Modbus, GPS, debug console, etc.
gpio pin, mode General-purpose digital I/O. Usually implied by digital_input/digital_output device types.
pwm pin, frequency, resolution PWM output. Implied by pwm_output device type.
adc pin, resolution Analog-to-digital conversion. Implied by analog_input.
onewire pin 1-Wire bus. Required for DS18B20 temperature sensors.
wifi ssid, host Wi-Fi network. Credentials are loaded from config, not hardcoded.
ethernet mac, ip Wired Ethernet (W5500 or similar).

Examples

hardware:
  buses:
    i2c_bus:
      interface: i2c
      sda: GPIO21
      scl: GPIO22

  devices:
    # Simple GPIO LED — pin is a direct field, no config: wrapper
    status_led:
      type: digital_output
      pin: GPIO13

    # I2C LCD — address/cols/rows are direct fields on the device
    display:
      type: lcd_i2c
      bus: i2c_bus
      address: 0x27
      cols: 16
      rows: 2

    # DS3231 RTC — channels auto-populated: hour, minute, second
    clock:
      type: ds3231
      bus: i2c_bus

Multi-channel sensors

Sensors that expose multiple readings (temperature + humidity, time components, etc.) declare a channels: list. Each channel becomes its own systemSensors.<name> float field.

✓ RTC devices (ds3231, ds1307) automatically populate [hour, minute, second] channels when no explicit channels: are declared.

channels: is a YAML sequence of channel name strings. Each string becomes a field in the generated SystemSensors struct.

hardware:
  devices:
    # BME280 — declare all three channels as a list of strings
    weather:
      type: bme280
      bus: i2c_bus
      channels: [temperature, humidity, pressure]

    # DHT22 — two channels
    env:
      type: dht22
      pin: GPIO4
      channels: [temperature, humidity]

    # DS3231 — explicit or omit (auto-populated)
    clock:
      type: ds3231
      bus: i2c_bus
      channels: [hour, minute, second, day, month, year]
ℹ When a device declares channels, log templates, MQTT topics, and telemetry entries must reference the channel names (not the device name). E.g. {temperature} not {weather}.

events:

Named system events that drive the state machine. Events from sensors, timers, GPIO, or MQTT can all be declared here.

⚠ events: is a mapping keyed by event name — not a list. A list causes a parse error. 
events:
  BUTTON_PRESSED:
    source: external
    description: User pressed the main button
  TEMP_HIGH:
    source: sensor
  CMD_START:
    source: mqtt
EVENT_NAME
Event identifier (the mapping key). required

Conventionally UPPER_SNAKE_CASE.

source
enum required

One of: external, timer, sensor, mqtt, internal, custom.

description
Human-readable note. optional
payload
Schema for event payload data. optional

parameters:

Runtime-tuneable values. Parameters become typed C++ variables initialized to their defaults; they can be read in guards and actions, and written via MQTT subscribe or serial commands.

parameters:
  temp_threshold:
    type: float
    default: 75.0
    range: [0.0, 120.0]   # or: min: 0.0  max: 120.0
    unit: °C
    description: Temperature at which cooling starts
    persist: true
type
enum required

One of: float, int, bool, string.

default
Initial value. required
range
[min, max] clamp bounds for numeric types. optional

Preferred form. Equivalent to separate min: and max: keys, which are also accepted.

unit
Display unit string (documentation only). optional
description
Human-readable note. optional
persist
bool optional

When true, the value is loaded from NVS/EEPROM at boot and saved when changed.

Parameter names are referenced in log strings and action params as {param_name}. See also: tasks: (every: accepts a parameter name as its interval).

actions:

Named driver invocations. Each action has a unique name, specifies a driver, and carries driver-specific parameters. Actions are referenced by name in tasks, transitions, commands, and state entry/exit hooks.

actions:
  turn_on_led:
    driver: gpio_control
    params:
      device: status_led
      value: true
driver
Driver plugin name. required
params
Driver-specific parameters map. optional
description
Human-readable note (reproduced as a comment in the generated stub). optional

Format strings

Template refs use {name} syntax. The name must match a declared sensor, channel, or parameter.

  • RTC channels ({hour}, {minute}, {second}) are formatted as %02d (two digits, zero-padded).
  • Float sensors are formatted as %.1f (one decimal place).
  • Literal % characters are automatically escaped.
  • Pure-literal strings (no refs) generate a direct print("...") without snprintf.
ℹ All {name} references in format strings are validated at parse time. An unknown name is a parse error, not a runtime bug.
oled_print Write text to an I2C OLED display (SSD1306)
device
Name of an oled_i2c device. required
text
Text to print. optional
row
int Text cursor line. optional

RTC driver

rtc_read Read time from a DS3231 or DS1307 RTC module (RTClib)
device
Name of a ds3231 or ds1307 device. required

Generates real RTClib code. For each declared (or auto-populated) channel, the generated snippet reads from DateTime _now = obj.now():

  • hour → systemSensors.hour = (float)_now.hour();
  • minute → systemSensors.minute = (float)_now.minute();
  • second → systemSensors.second = (float)_now.second();
  • day → systemSensors.day = (float)_now.day();
  • month → systemSensors.month = (float)_now.month();
  • year → systemSensors.year = (float)_now.year();

Complete RTC + LCD example

A full clock-on-display program written entirely in YAML, no manual C required:

pulseir: "1"

project:
  name: rtc_clock

target: esp32

hardware:
  buses:
    i2c_bus:
      interface: i2c
      sda: GPIO21
      scl: GPIO22
  devices:
    clock:
      type: ds3231
      bus: i2c_bus
    display:
      type: lcd_i2c
      bus: i2c_bus
      address: 0x27
      cols: 16
      rows: 2

actions:
  read_time:
    driver: rtc_read
    params: { device: clock }
  show_time:
    driver: lcd_display
    params:
      device: display
      format: {hour}:{minute}:{second}
      row: 0
      col: 3

tasks:
  clock_tick:
    every: 1000
    do: [read_time, show_time]

tasks:

Periodic background work. Each task runs its actions on a fixed interval. Tasks work with or without a state machine.

⚠ tasks: is a mapping keyed by task name — not a list. The action key is do:, not actions:. Both mistakes cause parse errors. 
tasks:
  sensor_poll:
    every: 2000            # milliseconds, or the name of an int parameter
    do: [read_temp, check_limits]
    log: T={temperature} H={humidity}
    description: Poll weather sensors every 2 seconds
task_name
Task identifier (the mapping key). required
every
int | string Interval in milliseconds, or the name of an int parameter. required

Using a parameter name (e.g. every: report_ms) makes the interval runtime-tuneable. See parameters:.

do
Action name or list of action names to run each tick. required (unless log: is set)

Names must be declared in the top-level actions: catalogue.

log
Format string printed after actions run. optional

Supports {sensor_name} and {parameter_name} template refs. All refs are validated at parse time. Requires a UART console bus.

description
Human-readable note. optional

commands:

Line-oriented command dispatch, typically over UART serial. Incoming lines are matched exactly; the matching entry runs its actions and/or raises an event.

⚠ Commands use a map: key (not a commands: list). Each entry in map: is keyed by the exact text the user types. The option flag is report_unknown: (underscore), not reportUnknown. 
commands:
  source: console           # name of a UART bus; defaults to the first declared UART
  report_unknown: true     # print "unknown command" when nothing matches
  map:
    # Short form: just a single action name (or a list)
    on: led_on
    off: led_off
    # Long form: run actions, raise an event, and/or print a reply
    start:
      do: [turn_on_pump]
      event: CMD_START
      log: Pump started
    status:
      log: temp={temperature} degC
source
Name of a declared UART interface. optional

Defaults to the project's console (first UART bus).

report_unknown
bool Print an error line when input doesn't match any command. optional, default true
map
Mapping of command string → handler. required

Command entry fields (long form)

command text
The exact string the user types (mapping key, trimmed). required
do
Action name or list of action names to run when matched. optional

Short form: set the entry value directly — on: led_on or on: [led_on, beep].

event
Event name to raise when matched (requires a state machine). optional
log
Reply line to print, with {name} template refs. optional
description
Human-readable note. optional

machine:

An optional hierarchical state machine (HSM). The machine section targets the PulseHSM runtime on Arduino. You can have tasks and commands without a machine, but a machine requires at least one state and one transition.

⚠ machine.states: is a mapping keyed by state name — not a list. machine.transitions: is the one true list. Transition trigger fields are on:, after:, every: — not event:, source:, target:. The action field is do:. 
machine:
  states:
    idle:
      entry: [turn_off_led]
    running:
      entry: [turn_on_led]
      exit:  [log_stop]
  transitions:
    - from: idle
      to:   running
      on:   CMD_START
    - from: running
      to:   idle
      after: 30000         # timeout in ms
      do:   [log_stop]

States

machine.states: is a mapping — each key is the state name. Composite states nest child states under a states: sub-mapping.

state_name
State identifier (the mapping key). required
entry
Action name or list of action names run on entering this state. optional
exit
Action name or list of action names run on leaving this state. optional
initial
Initial child state name (required when states: is present). optional
states
Child state mapping — makes this a composite state. optional
every / do
State-level periodic shorthand — equivalent to a self-transition with every: N and do: [...]. optional
description
Human-readable note. optional

Nested states example

machine:
  states:
    operating:
      initial: heating
      states:
        heating:
        cooling:

Nested state paths use / as separator: operating/heating.

Transitions

machine.transitions: is a list. Exactly one trigger key (on:, after:, or every:) is required per entry.

from
Source state path. Use * for wildcard (any state). required
to
Destination state path. omit for every: in-place transitions
on
Event name that triggers this transition. one of on/after/every
after
int | string Fire N ms after entering the source state. one of on/after/every
every
int | string Repeat do: actions every N ms without leaving the state. one of on/after/every
guard
Named C guard function that must return true for the transition to fire. optional
do
Action name or list of action names to run during the transition. optional
description
Human-readable note. optional
ℹ Guard functions are C stubs you implement: bool guard_<name>(const SystemContext* ctx). Guards live in C where they can be debugged and type-checked — PulseIR deliberately has no expression language. See actions: for the action catalogue they reference.

communication:

Explicit MQTT publish and subscribe contract. Without this block, the codegen publishes every sensor and subscribes every parameter and MQTT-sourced event. With it, only the listed items are wired.

communication:
  publish:
    - sensor: temperature
      topic: env/temp
    - sensor: humidity
  subscribe:
    - parameter: setpoint
      topic: ctrl/setpoint
    - event: CMD_START
publish[].sensor
Name of a declared sensor or channel. required
publish[].topic
Stable MQTT topic segment. optional — defaults to the sensor name
subscribe[].parameter
Parameter name to expose as a remotely-settable setpoint. one of
subscribe[].event
Event name to allow triggering via MQTT. one of
subscribe[].topic
Stable MQTT topic segment. optional — defaults to the parameter/event name
ℹ Machine state is always published when a state machine is declared — it does not need to appear in publish.

telemetry:

Per-channel MQTT publish intervals. Without this section, all sensors publish at the same global interval. With it, each channel can have its own interval — a fast temperature sensor and a slow diagnostic counter can coexist.

telemetry:
  interval_ms: 10000        # default for channels that omit their own
  topic_prefix: device/01  # defaults to project name
  channels:
    - sensor: temperature
      interval_ms: 2000
    - sensor: battery_v
      topic: health/battery
interval_ms
Default publish interval (ms or int parameter). required if any channel omits its own
topic_prefix
MQTT topic prefix. optional — defaults to project name
channels
Array of channel entries. required
channels[].sensor
Name of a declared sensor or channel. required
channels[].interval_ms
Per-channel override interval. optional
channels[].topic
Absolute MQTT topic override. optional

safety:

Pre-dispatch safety rules. runSafetyChecks() runs at the very top of loop(), before the HSM tick, so a critical fault preempts normal event dispatch. Rules reference C guard functions you write.

safety:
  rules:
    overtemp:
      check: temperature_above_limit
      description: Shut down if temperature exceeds 80°C
      severity: critical
      response: [turn_off_heater, sound_alarm]
      to: fault
      latching: true
      reset_when: temperature_safe
      restore: [silence_alarm]
rules.<name>.check
C guard function name — you implement bool check_fn(const SystemContext* ctx). required

Returns true when the condition is unsafe.

rules.<name>.description
Comment reproduced in the generated code. optional
rules.<name>.severity
critical | warning. Documentation only. optional
rules.<name>.response
Action names to invoke when the check fires. optional
rules.<name>.to
Target state to transition to when the check fires. Requires a state machine. optional
rules.<name>.latching
bool Once triggered, keeps acting on every loop even if check returns false. optional
rules.<name>.reset_when
C guard function that clears a latching fault. optional — latching only
rules.<name>.restore
Actions called when the latching fault clears. optional — latching only

diagnostics:

Runtime health and observability configuration: hardware watchdog, heartbeat LED, and log verbosity.

diagnostics:
  watchdog:
    timeout_s: 5             # seconds before watchdog fires; default 5
  heartbeat:
    pin: 2                   # GPIO pin to toggle; default 2 (built-in LED)
    interval_ms: 1000        # toggle interval; default 1000
  log_level: info            # verbose | info | warning | error | none
watchdog.timeout_s
int Watchdog timeout in seconds. optional, default 5
heartbeat.pin
int | string GPIO pin or parameter name. optional, default 2
heartbeat.interval_ms
int | string Toggle interval or parameter name. optional, default 1000
log_level
enum Serial trace verbosity. optional, default info

Values: verbose, info, warning, error, none.

libraries:

Declares third-party libraries the generated code depends on. Libraries implied by a built-in device type (Wire for I2C, SPI for SPI) do not need declaring — each backend knows its own platform's built-ins.

libraries:
  - name: PubSubClient
    include: PubSubClient.h
    version: "^2.8"
    source: registry
    description: MQTT client library
name
Library name as listed in the Arduino Library Manager. required
include
Header file to include. optional — defaults to <name>.h
version
Version constraint for the build system. optional
source
builtin | registry | git | local. optional
url
Repository or local path (for git and local sources). optional
description
Human-readable note. optional

imports:

Split a model across multiple YAML files. The entry file (the one with project:) lists what to include; the toolchain merges everything before compiling.

imports:
  - hardware.yaml
  - parameters.yaml
  - machine.yaml

Typical directory layout for a real project:

boiler/
├── pulse.yaml       ← entry file (project: + imports:)
├── hardware.yaml    ← buses and devices
├── parameters.yaml  ← tuneable values
└── machine.yaml     ← events, states, transitions, actions

Merge semantics

Name-keyed sections
hardware.devices, hardware.buses, events, actions, parameters, tasks, machine.states — merged by name. Declaring the same name in two files is a parse error, not a silent override.
List sections
machine.transitions, libraries — concatenated in import order; the importing file's entries come last.
project:
Only the entry file may declare it. A second declaration in an imported file is an error.
⚠ Circular imports are detected and reported as a parse error, naming every file in the cycle. The maximum import depth is 32 levels.

Paths resolve relative to the importing file, so subdirectories work. Pass the entry file to the CLI — the importer resolves the rest:

node dist/src/cli.js boiler/pulse.yaml --outdir build/boiler

Compiler Pipeline

Every model passes through the same stages before code is written. The pipeline is fail-fast: a hard error in any stage stops compilation and reports an actionable message.

YAML model (one file or a directory linked by imports:)
  ↓ SourceResolver + Merge
  ↓ Parser                  hard errors (unknown refs, malformed schema, pin conflicts)
  ↓ Board Resolver          logical pin → physical GPIO; HAL boundary + capability checks
  ↓ Validator               semantic warnings (unreachable states, unused actions, …)
  ↓ Optimizer               DCE + Task Merging   ← skip with --no-optimize
  ↓ Codegen
C++ / Python firmware

Optimizer

The optimizer runs two passes on the IR before codegen. It returns a new, leaner IR — the original is never mutated. Both passes are enabled by default; use --no-optimize to bypass them and compare raw vs. optimized output.

Dead Code Elimination (DCE)

Removes hardware that is declared but never used:

  • Dead components — devices whose pin identifier appears in no action params
  • Dead parameters — parameters referenced in no action param, log: template, or after: interval
  • Dead events — events that appear in no transition on: field

Removed items produce no #define, pinMode, enum value, or struct field in the generated sketch.

Task Merging

Tasks that share the same every: interval (in milliseconds) are fused into a single synthetic task named _merged_<N>ms. The scheduler then maintains one deadline per interval rather than N separate comparisons. Tasks with different intervals, or whose interval is a named parameter, are left unchanged.

# Before merging: two separate 200 ms timers in loop()
tasks:
  read_temp:  { every: 200, do: read_temperature }
  blink_led:  { every: 200, do: toggle_led }

# After merging: one _merged_200ms task calling both actions
ℹ Pass --no-optimize to bypass the entire optimizer and inspect the raw, unoptimized IR. Diff the two outputs to verify exactly what gets removed.

Validator warnings

The semantic validator runs after the parser and collects non-fatal warnings. Each has a machine-readable code printed alongside the message.

CodeWhat it catches
UNREACHABLE_STATEA leaf state that no transition ever targets and is not the initial state — it will never be entered.
UNUSED_EVENTAn event declared in events: but never referenced in any transition or command — almost always a typo in an on: field.
UNUSED_ACTIONAn action in the actions: catalogue that is never invoked from any transition, state entry/exit, task, or command. It will produce a dead stub function that is never called.
DUPLICATE_TRANSITIONTwo unguarded transitions from the same state on the same event. The second can never fire because the first always wins. (Guarded and wildcard-source transitions are excluded.)
PARTIAL_BINDINGA bus binding that declares some but not all pins in a required group — for example sda without scl. Declaring none is intentional (use board defaults); declaring half is almost always a copy-paste mistake.

HAL / board checks

When a --board is declared, the board resolver runs three checks after resolving logical pin names to physical GPIOs:

HAL boundary check

Derives the set of valid physical GPIOs from the board profile (pins: values ∪ pin_caps: keys) and verifies every device and bus pin against that set. A pin outside this set is a hard error:

✗ [HAL] Device "motor" is assigned to GPIO70, which does not exist on Arduino Uno. Check your target board — valid GPIO identifiers are derived from the board profile at boards/arduino_uno.yaml.

Bare numeric pins ("25") are normalised to "GPIO25" before the lookup, so both notations are accepted.

Capability check

Validates declared pins against capability tags in the board YAML:

  • reserved — pin wired to internal SPI flash or PSRAM; any use is a hard error
  • input_only — pin cannot drive output; assigning an output here is a hard error
  • strapping — boot-mode sensitive; driving it LOW at reset may prevent booting (warning)
  • ADC2 + Wi-Fi — ADC2 pins are unavailable while Wi-Fi is active on the ESP32 family (warning)

Framework compatibility

Warns when --target requests a framework the board's frameworks: list does not include.

Common Errors

The parser produces specific, actionable error messages. Here are the most frequent mistakes and what they mean.

Shape errors — list vs. mapping

✗ "tasks" is a list, but this schema keys it by name

You wrote tasks: (or events:, actions:, parameters:, machine.states:) as a YAML list (lines starting with -). Change it to a mapping keyed by name:

# Wrong:
tasks:
  - name: poll
    every: 1000
    actions: [read_sensor]

# Correct:
tasks:
  poll:
    every: 1000
    do: [read_sensor]

Unknown key in log/format string

✗ Task "poll" log references unknown name "temp_c"

All {name} references in log:, format:, and lines[].format are validated at parse time against declared sensors, channels, and parameters. Check the exact spelling — it must match a device or channel name (e.g. {temperature} for a channel named temperature), or a parameter name.

Missing trigger on transition

✗ Transition 2 has neither "on", "after", nor "every"

Every transition needs exactly one trigger. The old names event:, source:, and target: are not recognised — use on:, from:, and to:.

Task has no "every"

✗ Task "poll" has no "every". A task runs on an interval

every: is required for every task. It must be a positive integer (milliseconds) or the name of an int parameter. "200ms" is not valid — write 200.

Action not in catalogue

✗ State "idle" entry does "turn_on", which is not in the actions catalogue

All action names used in do:, state entry:/exit:, and transitions must be declared in the top-level actions: section first.

commands: declares no "map"

✗ commands: declares no "map", so no command would ever be recognised

The commands: block uses a map: key (not commands:) to list the dispatch table. See the commands section for the correct shape.

Unused action warning

⚠ [UNUSED_ACTION] Action "old_handler" is declared but never invoked — it will produce a stub function that is never called

An action in the top-level actions: catalogue is not referenced anywhere — no transition do:, no state entry:/exit:, no task, no command. This is almost always a leftover after a rename or a removed transition. Either delete the action declaration or add a reference to it.

Duplicate transition warning

⚠ [DUPLICATE_TRANSITION] Transition 3 (from "idle" on "START") duplicates transition 1 — both have no guard, so the second will never fire

Two unguarded transitions share the same source state and event. The state machine always picks the first matching transition, so the second is dead code. Add a guard: to differentiate them, or remove the duplicate.

HAL pin does not exist on board

✗ [HAL] Device "motor" is assigned to GPIO70, which does not exist on Arduino Uno. Check your target board — valid GPIO identifiers are derived from the board profile at boards/arduino_uno.yaml.

A device or bus pin references a GPIO that the target board does not have. This usually happens when switching boards without updating pin assignments — for example, a model written for the Arduino Mega (GPIO0–GPIO69) will fail on the Uno (GPIO0–GPIO19) if it uses GPIO20 or above. Update the pin to one that exists on the target board, or switch to a board with a larger GPIO set.
